## O que são mensagens livres?

Mensagens livres são mensagens que você envia **sem precisar de um template aprovado**. Você pode enviar texto, imagem, áudio, vídeo, documento — qualquer formato suportado — com total liberdade de conteúdo.

A única condição: a [janela de conversa](/conversation-window) de **24 horas** precisa estar aberta.

## Quando posso usar?

A janela abre quando o **cliente envia uma mensagem para você**. A partir desse momento, você tem 24 horas para enviar mensagens livres. Cada nova mensagem do cliente reinicia o timer.

```
Cliente envia mensagem → Janela abre (24h) → Você envia mensagens livres
```

## E se a janela estiver fechada?

Se o cliente não enviou mensagem nas últimas 24 horas, a janela está fechada. Nesse caso, a única opção é enviar um **template aprovado pela Meta** através do endpoint [Enviar template](/messages/send-template).

Depois que o cliente **responder** o template, a janela reabre e você volta a poder usar mensagens livres.

```
Janela fechada → Enviar template → Cliente responde → Janela reabre (24h)
```

<Info>
  Precisa enviar um template? Veja como na página [Enviar template](/messages/send-template). Para criar e gerenciar seus templates, acesse a seção [Templates](/templates/introduction).
</Info>

## Tipos disponíveis

Todos os endpoints desta seção utilizam a mesma rota:

`POST /v1/channels/{channelId}/messages`

O que muda é o campo `content.type`:

| Tipo | Descrição |
|---|---|
| `TEXT` | Mensagem de texto simples |
| `IMAGE` | Mensagem com imagem |
| `AUDIO` | Mensagem de áudio |
| `VIDEO` | Mensagem com vídeo |
| `CONTACT` | Envio de contato |
| `STICKER` | Sticker (figurinha) |
| `LOCATION` | Mensagem de localização |
| `INTERACTIVE_ACTION` | Mensagem com botões de ação (URL e ligar) |
| `INTERACTIVE_BUTTON` | Mensagem com botões de resposta rápida |
| `INTERACTIVE_LIST` | Lista de opções em seções — *em desenvolvimento* |
| `DOCUMENT` | Arquivo de até 100 MB, por URL ou Base64 |
| `REACTION` | Emoji em uma mensagem da conversa — *em desenvolvimento* |
| `LOCATION_REQUEST` | Pede a localização do cliente — *em desenvolvimento* |
| `FLOW` | Abre um formulário publicado — *em desenvolvimento* |
| `CATALOG` | Abre o catálogo da conta — *em desenvolvimento* |
| `PRODUCT` | Um produto do catálogo — *em desenvolvimento* |
| `PRODUCT_LIST` | Vitrine com seções — *em desenvolvimento* |
| `ORDER_DETAILS` | Fatura com pagamento — *em desenvolvimento* |
| `ORDER_STATUS` | Andamento do pedido — *em desenvolvimento* |
| `TEMPLATE` | Template aprovado pela Meta (fora da janela de 24h) |

## Resposta da API

Quando o envio é aceito, a API responde `200` com o identificador da mensagem:

```json
{
  "messageId": "01A0C92D0C957FE98B73C8BA0CACF741"
}
```

O `messageId` é uma string hexadecimal de 32 caracteres maiúsculos. Guarde esse valor: ele é necessário para reagir à mensagem ou citá-la depois.

<Note>
  Esse é o mesmo valor que chega no seu webhook como `message._id`. Use-o para reconciliar a chamada de envio com o evento recebido — veja a [estrutura dos payloads](/webhooks/payloads).
</Note>

## Responder citando uma mensagem

No canal Meta Cloud API, a mensagem pode sair como resposta a outra mensagem da conversa. No WhatsApp do cliente, ela aparece com o trecho da mensagem original em cima. Mande a referência da mensagem citada em `content.messageIdReply`:

```json
{
  "recipient": {
    "identifier": "5511999999999"
  },
  "content": {
    "type": "TEXT",
    "body": {
      "message": "Temos sim, no tamanho M."
    },
    "messageIdReply": "01A0C92D0C957FE98B73C8BA0CACF741"
  }
}
```

A referência pode ser:

- o `messageId` que a API devolveu no envio;
- o `message._id` do webhook, de mensagem recebida ou enviada;
- o `identifier` de um item de `contents` ou `attachments` do webhook.

A mensagem citada precisa ser do mesmo canal e da conversa com o mesmo contato do `recipient`. Em número do Brasil, o contato com e sem o nono dígito conta como o mesmo.

Saem citados os tipos `TEXT`, `IMAGE`, `AUDIO`, `VIDEO`, `DOCUMENT`, `STICKER`, `LOCATION`, `INTERACTIVE_BUTTON`, `INTERACTIVE_ACTION` e `INTERACTIVE_LIST`. `TEMPLATE`, `REACTION` e `CONTACT` não saem citados.

A API busca sozinha o id da mensagem citada na Meta. Não mande `content.integrationIdReply`: junto com `messageIdReply`, ele é ignorado; sozinho, faz a API recusar o envio.

Nos outros canais, a resposta não sai citada: a mensagem chega ao cliente como uma mensagem comum.

### Quando a API recusa a citação

A recusa acontece antes do envio: a mensagem não é enviada, não recebe `messageId` e não gera webhook.

| Status | `subCode` | Quando |
|---|---|---|
| `400` | — | `content.messageIdReply` vazio ou só com espaços, ou `content.integrationIdReply` sem `content.messageIdReply`. O `code` é `VALIDATION_ERROR`, e o campo vem em `message`: `"Field 'content.messageIdReply': ..."` |
| `422` | `REPLY_NOT_SUPPORTED` | O tipo da mensagem não sai citado |
| `422` | `QUOTED_MESSAGE_NOT_FOUND` | Nenhuma mensagem deste canal tem essa referência |
| `422` | `QUOTED_MESSAGE_OTHER_CHAT` | A mensagem citada é de uma conversa com outro contato |
| `422` | `QUOTED_MESSAGE_NOT_ACCEPTED` | A Meta recusou o envio da mensagem citada, então não há mensagem para citar no WhatsApp |

Nas recusas `422`, o `code` é `BUSINESS_RULE_VIOLATION`.

<Note>
  Para citar uma mensagem que você acabou de enviar, espere o webhook `MESSAGE_DELIVERY` dela. Antes disso, a citação pode dar `QUOTED_MESSAGE_NOT_FOUND`: nesse caso, repita a chamada depois do webhook.
</Note>

<Note>
  A Meta entrega a resposta sem o trecho citado quando a mensagem original foi apagada ou é antiga, normalmente com mais de 30 dias. A API não recusa a citação pela idade da mensagem.
</Note>

## Erros no envio

Quando a API recusa o envio, a mensagem não é enviada. A resposta traz o status HTTP do motivo e o código do erro:

```json
{
  "timestamp": "2026-10-22T14:00:00.123Z",
  "code": "BUSINESS_RULE_VIOLATION",
  "subCode": "CHANNEL_DISCONNECTED",
  "message": "Channel is disconnected"
}
```

| Campo | Descrição |
|---|---|
| `timestamp` | Data e hora da recusa, em UTC |
| `code` | Categoria do erro |
| `subCode` | Código do caso. Só vem quando o caso tem um código próprio |
| `message` | Descrição do erro. O texto pode mudar: trate o erro por `code` e `subCode` |

### Canal desconectado

Se o canal não estiver conectado no momento da chamada, a API responde `422` com `code` `BUSINESS_RULE_VIOLATION` e `subCode` `CHANNEL_DISCONNECTED`, o corpo do exemplo acima. A mensagem não é enviada e não fica guardada para sair depois.

Para voltar a enviar, conecte o canal de novo (veja [Conectar um canal](/connect/introduction)) e repita a chamada.

### Outros erros

| Status | `code` | Quando |
|---|---|---|
| `400` | `VALIDATION_ERROR` | O corpo não serve para o tipo da mensagem: um `content.type` que não existe ou um campo obrigatório ausente. O campo vem em `message`, como `"Field 'content.type': invalid value"` |
| `422` | `BUSINESS_RULE_VIOLATION` | Outra regra de envio recusou a mensagem. Sem `subCode`, o motivo está só em `message` |
| `502` | — | Falha do nosso lado ao processar o envio. O corpo traz `"error": "integration_unavailable"`, ou `code` com a `message` fixa `"Message sending failed"` |

<Note>
  Recusas feitas antes de a mensagem seguir para o envio, como Secret Key inválida ou assinatura inativa, vêm em outro formato, só com o campo `error`.
</Note>
