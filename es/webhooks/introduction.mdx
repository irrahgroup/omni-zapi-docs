## ¿Qué son los webhooks?

Los webhooks son notificaciones HTTP que {projectName} envía a tu servidor cuando ocurre un evento, como la recepción de un mensaje, un estado de entrega o la actualización de una plantilla.

En lugar de que tu sistema consulte la API periódicamente (polling), {projectName} **te envía los eventos** en el momento en que ocurren.

```
Ocurre un evento → Z-API Omni → POST a tu URL → Tu sistema lo procesa
```

<Note>
  Cualquier secret key válida de un workspace activo puede gestionar webhooks: de canal, predeterminado y global. No hace falta ningún rol específico en tu cuenta. Si el workspace no está activo, las llamadas de webhooks devuelven `422` con `{"error": "Webhook management requires an active workspace"}`.
</Note>

{projectName} tiene tres tipos de webhook. Lo que **cambia** entre ellos son los eventos admitidos y la forma de asociarlos; cada sección detalla sus particularidades. El resto de esta página aplica a **los tres tipos**.

## Formatos de payload

{projectName} admite tres formatos de payload:

| Formato | Descripción |
|---|---|
| `DEFAULT` | Formato estándar de Z-API Omni |
| `Z_API` | Formato compatible con Z-API: mantiene la estructura que tus integraciones ya procesan, ideal si estás migrando |
| `CHATWOOT` | El formato que espera Chatwoot, para conectar el canal directamente a su bandeja de entrada |

<Note>
  El [webhook global](/es/webhooks/template-webhooks) se entrega en `DEFAULT`: usa siempre `DEFAULT` en él. Con `ACCOUNT_RESTRICTION` o con los eventos de la plataforma (facturación y `CHANNEL_DISCONNECTED`), otro formato devuelve `422`. El webhook predeterminado no admite `CHATWOOT`.
</Note>

## URL del webhook

Al crear un webhook, y al cambiar la URL de uno existente, {projectName} comprueba la `url` antes de guardarla. Las reglas valen para los tres tipos de webhook.

| Regla | Si no se cumple |
|---|---|
| URL absoluta, con `http` o `https`, de hasta 2048 caracteres | `400` con `{"error": "Invalid webhook URL: use an absolute http or https URL up to 2048 characters"}` |
| El host existe en el DNS y resuelve solo a direcciones públicas | `400` con `{"error": "Webhook URL not allowed: the host must resolve only to public addresses"}` |

El host se rechaza cuando:

- es una IP que no es pública: red privada, loopback, link-local (incluida la dirección de metadatos de la nube `169.254.169.254`), CGNAT, multicast o un rango reservado, en IPv4 o IPv6;
- es un nombre que resuelve a una de esas direcciones. Basta con una dirección no pública entre las que devuelve el nombre;
- es `localhost`, termina en `.localhost` o `.internal`, o es un nombre sin punto, como `https://servidor/webhook`;
- es una IPv4 escrita fuera de la forma habitual de cuatro números decimales, como `http://2130706433/`;
- no existe en el DNS o no tiene dirección.

Si el DNS no responde a tiempo, la respuesta es `503` con `{"error": "Could not verify the webhook URL now, try again"}`. No se guarda nada: inténtalo de nuevo.

<Note>
  `http` se sigue aceptando, pero es preferible `https`: con `http`, el cuerpo del evento y los headers de autenticación viajan sin cifrar.
</Note>

<Note>
  En la actualización, la `url` solo se comprueba cuando cambia. Un `PATCH` sin `url`, o con la misma URL ya guardada, no se rechaza por ella: un webhook antiguo cuya URL hoy se rechazaría puede seguir deshabilitándose, cambiando otros campos o eliminándose.
</Note>

## Autenticación del webhook

Puedes configurar cómo se autentica {projectName} al llamar a tu URL:

| Tipo | Cómo funciona |
|---|---|
| `NONE` | Sin autenticación (no recomendado en producción) |
| `BEARER` | Envía `Authorization: Bearer <token>` |
| `API_KEY` | Envía una clave de API configurada |
| `BASIC` | HTTP Basic Authentication (`username:password`) |
| `CUSTOM_HEADER` | Envía un header personalizado con el nombre y el valor que definas |

## Firma HMAC

Para asegurarte de que las peticiones que recibes provienen realmente de {projectName} y no han sido manipuladas, habilita la firma HMAC indicando `signing: true` al crear el webhook.

Cuando está habilitada:
- Se genera un `secret` de 64 caracteres hexadecimales, que se devuelve **una sola vez**, en la creación o la actualización.
- Cada petición enviada a tu webhook trae el header `x-webhook-signature`, con el formato `t={unix_timestamp},v1={hmac_sha256_hex}`.
- Verificas la firma en tu servidor usando el `secret` que has almacenado.

<Warning>
  La firma **no** es el HMAC solo del cuerpo. Se calcula sobre una cadena canónica de cinco campos, de la cual el cuerpo es el último. Consulta [Firma HMAC](/es/webhooks/signature) para la cadena exacta, un ejemplo completo y código de validación listo para usar.
</Warning>

<Warning>
  El `secret` se muestra **únicamente** en la respuesta de creación o de actualización con `signing: true`. Guárdalo de forma segura: no se puede recuperar después.
</Warning>
