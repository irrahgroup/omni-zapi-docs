## ¿Qué son los mensajes libres?

Los mensajes libres son mensajes que envías **sin necesidad de una plantilla aprobada**. Puedes enviar texto, imagen, audio, vídeo o documento —cualquier formato compatible— con total libertad de contenido.

La única condición es que la [ventana de conversación](/es/conversation-window) de **24 horas** esté abierta.

## ¿Cuándo puedo usarlos?

La ventana se abre cuando el **cliente te envía un mensaje**. A partir de ese momento tienes 24 horas para enviar mensajes libres. Cada mensaje nuevo del cliente reinicia el contador.

```
El cliente envía un mensaje → La ventana se abre (24 h) → Envías mensajes libres
```

## ¿Y si la ventana está cerrada?

Si el cliente no ha enviado ningún mensaje en las últimas 24 horas, la ventana está cerrada. En ese caso, la única opción es enviar una **plantilla aprobada por Meta** mediante el endpoint [Enviar plantilla](/es/messages/send-template).

Cuando el cliente **responda** a la plantilla, la ventana se reabre y vuelves a poder usar mensajes libres.

```
Ventana cerrada → Enviar plantilla → El cliente responde → La ventana se reabre (24 h)
```

<Info>
  ¿Necesitas enviar una plantilla? Descubre cómo en la página [Enviar plantilla](/es/messages/send-template). Para crear y gestionar tus plantillas, consulta la sección [Plantillas](/es/templates/introduction).
</Info>

## Tipos disponibles

Todos los endpoints de esta sección utilizan la misma ruta:

`POST /v1/channels/{channelId}/messages`

Lo que cambia es el campo `content.type`:

| Tipo | Descripción |
|---|---|
| `TEXT` | Mensaje de texto simple |
| `IMAGE` | Mensaje con imagen |
| `AUDIO` | Mensaje de audio |
| `VIDEO` | Mensaje con vídeo |
| `CONTACT` | Envío de un contacto |
| `STICKER` | Sticker |
| `LOCATION` | Mensaje de ubicación |
| `INTERACTIVE_ACTION` | Mensaje con botones de acción (abrir URL y llamar) |
| `INTERACTIVE_BUTTON` | Mensaje con botones de respuesta rápida |
| `INTERACTIVE_LIST` | Lista de opciones en secciones — *en desarrollo* |
| `DOCUMENT` | Archivo de hasta 100 MB, por URL o Base64 |
| `REACTION` | Emoji en un mensaje de la conversación — *en desarrollo* |
| `LOCATION_REQUEST` | Pide la ubicación del cliente — *en desarrollo* |
| `FLOW` | Abre un formulario publicado — *en desarrollo* |
| `CATALOG` | Abre el catálogo de la cuenta — *en desarrollo* |
| `PRODUCT` | Un producto del catálogo — *en desarrollo* |
| `PRODUCT_LIST` | Vitrina con secciones — *en desarrollo* |
| `ORDER_DETAILS` | Factura con pago — *en desarrollo* |
| `ORDER_STATUS` | Avance del pedido — *en desarrollo* |
| `TEMPLATE` | Plantilla aprobada por Meta (fuera de la ventana de 24 h) |

## Respuesta de la API

Cuando se acepta el envío, la API responde `200` con el identificador del mensaje:

```json
{
  "messageId": "01A0C92D0C957FE98B73C8BA0CACF741"
}
```

El `messageId` es una cadena hexadecimal de 32 caracteres en mayúsculas. Guarda este valor: lo necesitas para reaccionar al mensaje o citarlo más adelante.

<Note>
  Este es el mismo valor que llega a tu webhook como `message._id`. Úsalo para reconciliar la llamada de envío con el evento recibido — consulta la [estructura de los payloads](/es/webhooks/payloads).
</Note>

## Responder citando un mensaje

En el canal Meta Cloud API, un mensaje puede salir como respuesta a otro mensaje de la conversación. En el WhatsApp del cliente, aparece con el fragmento del mensaje original encima. Envía la referencia del mensaje citado en `content.messageIdReply`:

```json
{
  "recipient": {
    "identifier": "5511999999999"
  },
  "content": {
    "type": "TEXT",
    "body": {
      "message": "Sí, lo tenemos en talla M."
    },
    "messageIdReply": "01A0C92D0C957FE98B73C8BA0CACF741"
  }
}
```

La referencia puede ser:

- el `messageId` que la API devolvió en el envío;
- el `message._id` del webhook, de un mensaje recibido o enviado;
- el `identifier` de un elemento de `contents` o `attachments` del webhook.

El mensaje citado tiene que ser del mismo canal y de la conversación con el mismo contacto del `recipient`. En números de Brasil, el contacto con y sin el noveno dígito cuenta como el mismo.

Salen citados los tipos `TEXT`, `IMAGE`, `AUDIO`, `VIDEO`, `DOCUMENT`, `STICKER`, `LOCATION`, `INTERACTIVE_BUTTON`, `INTERACTIVE_ACTION` e `INTERACTIVE_LIST`. `TEMPLATE`, `REACTION` y `CONTACT` no salen citados.

La API busca sola el id del mensaje citado en Meta. No envíes `content.integrationIdReply`: junto con `messageIdReply`, se ignora; solo, hace que la API rechace el envío.

En los demás canales, la respuesta no sale citada: el mensaje llega al cliente como un mensaje normal.

### Cuándo la API rechaza la cita

El rechazo ocurre antes del envío: el mensaje no se envía, no recibe `messageId` y no genera webhook.

| Estado | `subCode` | Cuándo |
|---|---|---|
| `400` | — | `content.messageIdReply` vacío o solo con espacios, o `content.integrationIdReply` sin `content.messageIdReply`. El `code` es `VALIDATION_ERROR`, y el campo viene en `message`: `"Field 'content.messageIdReply': ..."` |
| `422` | `REPLY_NOT_SUPPORTED` | El tipo de mensaje no sale citado |
| `422` | `QUOTED_MESSAGE_NOT_FOUND` | Ningún mensaje de este canal tiene esa referencia |
| `422` | `QUOTED_MESSAGE_OTHER_CHAT` | El mensaje citado es de una conversación con otro contacto |
| `422` | `QUOTED_MESSAGE_NOT_ACCEPTED` | Meta rechazó el envío del mensaje citado, así que no hay mensaje para citar en WhatsApp |

En los rechazos `422`, el `code` es `BUSINESS_RULE_VIOLATION`.

<Note>
  Para citar un mensaje que acabas de enviar, espera su webhook `MESSAGE_DELIVERY`. Antes de eso, la cita puede devolver `QUOTED_MESSAGE_NOT_FOUND`: en ese caso, repite la llamada después del webhook.
</Note>

<Note>
  Meta entrega la respuesta sin el fragmento citado cuando el mensaje original fue borrado o es antiguo, normalmente con más de 30 días. La API no rechaza la cita por la antigüedad del mensaje.
</Note>

## Errores al enviar

Cuando la API rechaza el envío, el mensaje no se envía. La respuesta trae el estado HTTP del motivo y el código del error:

```json
{
  "timestamp": "2026-10-22T14:00:00.123Z",
  "code": "BUSINESS_RULE_VIOLATION",
  "subCode": "CHANNEL_DISCONNECTED",
  "message": "Channel is disconnected"
}
```

| Campo | Descripción |
|---|---|
| `timestamp` | Fecha y hora del rechazo, en UTC |
| `code` | Categoría del error |
| `subCode` | Código del caso. Solo viene cuando el caso tiene un código propio |
| `message` | Descripción del error. El texto puede cambiar: trata el error por `code` y `subCode` |

### Canal desconectado

Si el canal no está conectado en el momento de la llamada, la API responde `422` con `code` `BUSINESS_RULE_VIOLATION` y `subCode` `CHANNEL_DISCONNECTED`, el cuerpo del ejemplo anterior. El mensaje no se envía y no queda guardado para salir después.

Para volver a enviar, conecta el canal de nuevo (consulta [Conectar un canal](/es/connect/introduction)) y repite la llamada.

### Otros errores

| Estado | `code` | Cuándo |
|---|---|---|
| `400` | `VALIDATION_ERROR` | El cuerpo no sirve para el tipo de mensaje: un `content.type` que no existe o un campo obligatorio ausente. El campo viene en `message`, como `"Field 'content.type': invalid value"` |
| `422` | `BUSINESS_RULE_VIOLATION` | Otra regla de envío rechazó el mensaje. Sin `subCode`, el motivo está solo en `message` |
| `502` | — | Fallo de nuestro lado al procesar el envío. El cuerpo trae `"error": "integration_unavailable"`, o `code` con el `message` fijo `"Message sending failed"` |

<Note>
  Los rechazos hechos antes de que el mensaje pase al envío, como una Secret Key no válida o una suscripción inactiva, llegan en otro formato, solo con el campo `error`.
</Note>
