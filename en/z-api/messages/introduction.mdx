## Overview

The message endpoints in this section allow you to send messages **only when the WhatsApp conversation window is open** (within the 24-hour period). This is a rule from the official WhatsApp Business API.

<Warning>
  The 24-hour conversation window opens when the **customer sends a message to you**. Outside this window, you can only send messages using **Meta-approved templates**. The messages in this section **do not work** outside the conversation window.
</Warning>

### Inside the window (24h)

Did the customer send you a message? Great, the window is open. You can use any endpoint in this section to reply with text, image, audio, video, document, etc.

### Outside the window (after 24h)

If the customer has **not** sent a message in the last 24 hours, the only way to start a conversation is by sending a **message template** previously approved by Meta. Templates are pre-defined messages that you create and submit for approval in the Meta dashboard.

<Info>
  In Z-API (unofficial connection) this limitation didn't exist — you could send messages at any time. In the official API, this rule is mandatory and cannot be bypassed.
</Info>

---

To send a message, you need the recipient's **phone number**, including the country code.

| Format | Example |
|---|---|
| Country code + area code + number | `5511999999999` |

## Request body

Send the body as JSON, with the `Content-Type: application/json` header, or as a form, with `Content-Type: application/x-www-form-urlencoded` or `multipart/form-data`. In the form, only the simple fields are read, such as `phone`, `message`, `image` and `caption`. Lists and objects, such as `buttonActions`, `optionList` and `contacts`, only go in JSON.

With another `Content-Type`, such as `text/plain`, or without the header, the body is not read and the send is refused with `400`. The error usually reports a required field as missing, even when it is in the body: for example, `{"error": "phone is required"}` or, on `send-text`, `{"error": "message is required"}`.

With `Content-Type: application/json` and a body that is not valid JSON, the response is also `400`, with the JSON read error. For example: `{"error": "invalid character 'h' looking for beginning of value"}`.

## API Response

When you send a message, the API returns the same response structure you already know from Z-API. This means **no changes are needed** in your code that processes the returns — the fields, types, and formats are identical.

Example response when sending a message:

```json
{
  "zaapId": "3999984263738042930CD6ECDE9VDWSA",
  "messageId": "D241XXXX732339502B68"
}
```

<Note>
  We maintain full compatibility with the Z-API response structure. If your application already handles these fields, it will continue working without changes.
</Note>

### Store the messageId

It's very important that you **store the `messageId`** returned, as it's needed for future operations, like reacting to the message. To [mark as read](/en/z-api/messages/read-message) a received message, use the `messageId` that came in the webhook.

<Warning>
  Without the `messageId`, you won't be able to reference the message later to react.
</Warning>

## Sending errors

After the checks of each route, the send can still fail while preparing the media or on its way to the channel. In that case the message is not sent, and the response is one of these:

| Status | `error` | When |
|---|---|---|
| `422` | `failed to send message: Channel is disconnected: ...` | The channel is disconnected. The text says how to reconnect each channel type |
| `422` | `this channel does not support sending messages yet` | The channel does not send through this route yet |
| `400` | `failed to send message: ...`, with the media problem | The media was refused. The texts are below |
| `400` | `failed to decode base64: ...` | The base64 media does not decode, such as `data:image/png;base64,` followed by content that is not base64 |
| `503` | `<failure>: a configuration problem on our side ...` or `<failure>: a temporary failure on our side ...` | A failure on our side, of configuration or temporary. It was not caused by the request, and nothing was sent. The texts are below and say when to try again |
| `502` | `failed to upload media` | Failed to store the media sent in base64 |
| `502` | `failed to send message` | Other sending failures |

The texts of the media `400`:

- `failed to send message: media too large for this channel: send a smaller file`
- `failed to send message: caption too long: use at most 1024 characters`
- `failed to send message: media URL is required: send the media URL or base64 in the media field of this route`
- `failed to send message: invalid base64 media: send data:<mime type>;base64,<content> or a media URL`
- `failed to send message: media type not supported by this route`
- `failed to send message: media refused: check the media URL and its type`

The texts of the `503`, where `<failure>` says what failed, such as `failed to send message`:

- `<failure>: a configuration problem on our side stopped this request. It was not caused by your request, and nothing was done. Try again later; if it persists, contact support`
- `<failure>: a temporary failure on our side stopped this request. It was not caused by your request, and nothing was done. Try again in a few seconds; if it persists, contact support`

<Note>
  The `200` confirms the send was accepted, not delivered. If WhatsApp refuses the message later, for example on Official WhatsApp outside the 24-hour window, the message does not arrive, and the failure comes in the message status webhook (`MESSAGE_STATUS`). See [channel webhooks](/en/webhooks/channel-webhooks).
</Note>

## Text formatting

You can format message text using WhatsApp special characters:

| Formatting | Syntax | Result |
|---|---|---|
| **Bold** | `*text*` | **text** |
| _Italic_ | `_text_` | _text_ |
| ~~Strikethrough~~ | `~text~` | ~~text~~ |
| `Monospace` | `` ```text``` `` | `text` |
