## Overview

Partially updates a webhook's configuration. Only the fields sent in the body are updated — the rest remain unchanged.

### Updating events

When sending the `events` field, the list replaces the webhook's events:

```json
{ "events": ["MESSAGE_RECEIVED", "MESSAGE_STATUS", "CONNECTED"] }
```

- The list cannot be empty: `"events": []` returns `400` with `{"error": "Events cannot be empty when provided"}`. To keep the events, omit the field.
- An item that is null, blank, or a name that does not exist returns `400` with `{"error": "events contains an unknown or empty event name"}`, and nothing is changed.
- An event the channel type does not emit returns `422` (see [Events by channel type](/en/webhooks/channel-webhooks#events-by-channel-type)). An event already stored on the webhook is still accepted.

<Note>
  **Event the API does not know yet.** A webhook may have a stored event that this version of the API does not know yet, for example a new event subscribed from the dashboard before it reached the API. That event does not appear in `events` in the responses, and it is kept when you replace the events: the `PATCH` replaces only the events the API knows. A webhook that only has events like that appears with `events: []`.
</Note>

### Changing the URL

The new `url` follows the same rules as on creation (see [Webhook URL](/en/webhooks/introduction#webhook-url)). It is only checked when it changes: a `PATCH` without `url`, or with the URL already stored, is not refused because of it.

### Enabling or rotating HMAC signing

If you send `signing: true`, a new `secret` is generated and returned in this response. Use this also to **rotate** the secret without recreating the webhook.

```json
{ "signing": true }
```

<Warning>
  The new `secret` is returned **only in this response**. Store it before closing the session.
</Warning>

<Warning>
  `signing: true` rotates the secret **every time**, including when signing was already enabled and you only meant to change another field in the same request. To avoid rotating, **omit** the `signing` field.
</Warning>

To verify the signature with the new secret, see [HMAC signing](/en/webhooks/signature).

### Removing HMAC signing

```json
{ "signing": false }
```

The webhook stops sending the `x-webhook-signature` header. The response carries `"signing": false` and `"secret": null`.

### Changing the authentication

Send the authentication in the nested form, in `auth`, or in the flat form, with `authType` and the credential for the type (`token` for `BEARER`, `key` for `API_KEY`):

```json
{ "auth": { "type": "BEARER", "token": "new-secret-token" } }
```

```json
{ "authType": "API_KEY", "key": "new-key" }
```

`BASIC` (`username` and `password`) and `CUSTOM_HEADER` (`headerName` and `headerValue`) only exist in the nested form. `authType` `NONE` clears the authentication.

### Switching to the `CHATWOOT` format

When you send `payloadFormat` `CHATWOOT`, also send `customAttributes` with numeric `chatwoot_account_id` and `chatwoot_inbox_id` greater than zero:

| Case | Response |
|---|---|
| `CHATWOOT` without `customAttributes` | `400` with `{"error": "Account ID e Inbox ID do Chatwoot sao obrigatorios ao trocar para o formato CHATWOOT"}` |
| `chatwoot_account_id` missing, not numeric or less than 1 | `400` with `{"error": "Chatwoot Account ID e obrigatorio (numero > 0) quando o formato e CHATWOOT"}` |
| `chatwoot_inbox_id` missing, not numeric or less than 1 | `400` with `{"error": "Chatwoot Inbox ID e obrigatorio (numero > 0) quando o formato e CHATWOOT"}` |

### Temporarily disabling

```json
{ "status": "DISABLED" }
```

The webhook stops receiving events while `DISABLED`. To reactivate:

```json
{ "status": "ENABLED" }
```

A `status` other than `ENABLED` or `DISABLED` returns `400` with `{"error": "status must be one of [ENABLED, DISABLED]"}`.

<Note>
  The `webhookId` is obtained from the [Create webhook](/en/webhooks/create-webhook) or [List webhooks](/en/webhooks/list-webhooks) endpoint.
</Note>
