## What are webhooks?

Webhooks are HTTP notifications that {projectName} sends to your server when events happen — such as a message received, delivery status, or a template update.

Instead of your system periodically polling the API, {projectName} **pushes events to you** as they happen.

```
Event happens → Z-API Omni → POST to your URL → Your system processes it
```

<Note>
  Any valid secret key of an active workspace can manage webhooks: channel, default and global. No specific role is required on your account. If the workspace is not active, webhook calls return `422` with `{"error": "Webhook management requires an active workspace"}`.
</Note>

## Webhook types

{projectName} has three webhook types. What **differs** between them is the accepted events and how they are associated — each section covers its own specifics. The rest of this page applies to **all three types**.

## Payload formats

{projectName} supports three payload formats:

| Format | Description |
|---|---|
| `DEFAULT` | Standard Z-API Omni format |
| `Z_API` | Z-API compatible format — keeps the structure your integrations already handle, ideal when migrating |
| `CHATWOOT` | The format Chatwoot expects, to plug the channel straight into its inbox |

<Note>
  The [global webhook](/en/webhooks/template-webhooks) is delivered in `DEFAULT`: always use `DEFAULT` on it. With `ACCOUNT_RESTRICTION` or the platform events (billing and `CHANNEL_DISCONNECTED`), another format returns `422`. The default webhook does not accept `CHATWOOT`.
</Note>

## Webhook URL

When you create a webhook, and when you change the URL of an existing one, {projectName} checks the `url` before saving it. The rules apply to all three webhook types.

| Rule | If it is not met |
|---|---|
| Absolute URL, `http` or `https`, up to 2048 characters | `400` with `{"error": "Invalid webhook URL: use an absolute http or https URL up to 2048 characters"}` |
| The host exists in DNS and resolves only to public addresses | `400` with `{"error": "Webhook URL not allowed: the host must resolve only to public addresses"}` |

The host is refused when it:

- is an IP that is not public: private network, loopback, link-local (including the cloud metadata address `169.254.169.254`), CGNAT, multicast, or a reserved range, in IPv4 or IPv6;
- is a name that resolves to one of those addresses. A single non-public address among the ones the name returns is enough;
- is `localhost`, ends in `.localhost` or `.internal`, or is a name without a dot, such as `https://server/webhook`;
- is an IPv4 address written outside the usual four decimal numbers, such as `http://2130706433/`;
- does not exist in DNS or has no address.

If DNS does not answer in time, the response is `503` with `{"error": "Could not verify the webhook URL now, try again"}`. Nothing is saved: try again.

<Note>
  `http` is still accepted, but prefer `https`: with `http`, the event body and the authentication headers travel unencrypted.
</Note>

<Note>
  On update, the `url` is only checked when it changes. A `PATCH` without `url`, or with the URL already stored, is not refused because of it: an old webhook whose URL would be refused today can still be disabled, have other fields changed, or be deleted.
</Note>

## Webhook authentication

You can configure how {projectName} authenticates when calling your URL:

| Type | How it works |
|---|---|
| `NONE` | No authentication (not recommended in production) |
| `BEARER` | Sends `Authorization: Bearer <token>` |
| `API_KEY` | Sends a configured API key |
| `BASIC` | HTTP Basic Authentication (`username:password`) |
| `CUSTOM_HEADER` | Sends a custom header with a name and value you define |

## HMAC signing

To ensure requests received are genuinely from {projectName} and have not been tampered with, enable HMAC signing by setting `signing: true` when creating the webhook.

When enabled:
- A 64-character hexadecimal `secret` is generated and returned **only once** on create/update.
- Each request sent to your webhook carries the `x-webhook-signature` header, in the form `t={unix_timestamp},v1={hmac_sha256_hex}`.
- You verify the signature on your server using the stored `secret`.

<Warning>
  The signature is **not** the HMAC of the body alone. It is computed over a canonical string of five fields, of which the body is the last. See [HMAC signing](/en/webhooks/signature) for the exact string, a complete example, and ready-to-use verification code.
</Warning>

<Warning>
  The `secret` is shown **only** in the create response or in an update with `signing: true`. Store it securely — it cannot be retrieved afterwards.
</Warning>
