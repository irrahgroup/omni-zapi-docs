## Overview

Partially updates a global webhook's configuration. Only the fields sent in the body are updated; the rest remain unchanged.

### Updating events

When sending the `events` field, the list replaces the existing events and must contain **only** account events: `UPDATE_TEMPLATE_STATUS`, `UPDATE_TEMPLATE_CATEGORY`, the five billing events (`BILLING_PAYMENT_FAILED`, `BILLING_PAYMENT_RECOVERED`, `BILLING_SUBSCRIPTION_CANCELED`, `BILLING_INSTANCE_SUSPENDED`, `BILLING_INSTANCE_RELEASED`), `ACCOUNT_RESTRICTION` and `CHANNEL_DISCONNECTED` (otherwise → `422`). See [Accepted events](/en/webhooks/template-webhooks#accepted-events):

```json
{ "events": ["UPDATE_TEMPLATE_STATUS", "UPDATE_TEMPLATE_CATEGORY"] }
```

- The list cannot be empty: `"events": []` returns `400` with `{"error": "Events cannot be empty when provided"}`. To keep the events, omit the field.
- An item that is null, blank, or a name that does not exist returns `400` with `{"error": "events contains an unknown or empty event name"}`, and nothing is changed.

<Note>
  **Event the API does not know yet.** A webhook may have a stored event that this version of the API does not know yet, for example a new event subscribed from the dashboard before it reached the API. That event does not appear in `events` in the responses, and it is kept when you replace the events: the `PATCH` replaces only the events the API knows. A webhook that only has events like that appears with `events: []`.
</Note>

### Changing the URL

The new `url` follows the same rules as on creation (see [Webhook URL](/en/webhooks/introduction#webhook-url)). It is only checked when it changes: a `PATCH` without `url`, or with the URL already stored, is not refused because of it.

### HMAC signing

`signing: true` generates a new `secret` (returned only in this response); `signing: false` removes signing.

<Warning>
  The new `secret` is returned **only in this response**. Store it before closing the session.
</Warning>

<Warning>
  `signing: true` rotates the secret **every time**, including when signing was already enabled and you only meant to change another field in the same request. To avoid rotating, **omit** the `signing` field.
</Warning>

To verify the signature, see [HMAC signing](/en/webhooks/signature).

### Temporarily disabling

```json
{ "status": "DISABLED" }
```

To reactivate, send `{ "status": "ENABLED" }`.

A `status` other than `ENABLED` or `DISABLED` returns `400` with `{"error": "status must be one of [ENABLED, DISABLED]"}`.

### Delivery format: use `DEFAULT`

The global webhook is delivered in the `DEFAULT` format. Send `payloadFormat` `DEFAULT` or omit the field.

| Case | Response |
|---|---|
| `events` with `ACCOUNT_RESTRICTION` and `payloadFormat` `Z_API` or `CHATWOOT` | `422` with `{"error": "ACCOUNT_RESTRICTION only supports DEFAULT payload format"}` |
| The webhook would be left with platform events (billing or `CHANNEL_DISCONNECTED`) in a format other than `DEFAULT` | `422` with `{"error": "Platform events are delivered only in DEFAULT payload format"}` |

The check uses the final state the request would leave: the events sent (or the stored ones, if `events` is omitted) and the format sent (or the stored one). Nothing is changed when the request is refused.

<Note>
  After the change, routing may take up to ~5 min to reflect (cache TTL).
</Note>
